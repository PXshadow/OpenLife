1. Goals and non-goals

Goals

  • Rust game server (OHOL-compatible protocol)
  • Multi-core from day one; low lock contention
  • Worlds far larger than ~500×500, still dynamic
  • Rule AI + optional LLM AI on the server
  • Web hosts site + live stats + family trees
  • No SQL/Redis runtime dependency
  • Structured metrics for automated evolution
  • Grok Build work paced under 80% quota

Non-goals (now)

  • Full client rewrite
  • Pixel-perfect day-one parity with every Haxe quirk
  • External database requirement
  • Multi-region cluster (design may allow later sharding)

3. Research findings — current architecture

Runtime topology (Haxe today)

main thread
  └─ TimeHelper.DoTimeLoop()          ~20 Hz simulation
       ├─ player vitals, move, temperature
       ├─ world map slice (1/WorldTimeParts)
       ├─ respawn / long-term decay
       └─ periodic save / backup

ThreadServer (accept)
  └─ Thread per TCP connection
       └─ read until '#' → Server.process (mutex-guarded)

AiBase.StartAiThread()
  └─ single loop over all ServerAi → doTimeStuff

WebServer
  └─ HTTP accept → thread per request → HTML stats

Data model (simplified)

DomainTodayNotes
WorldFlat vectors W×Hbiomes, floors, objects, helpers, hidden, heat
Map genPNG → biometoroidal wrap; sample map 500×500
Contentobjects + transitions txt~4k objects, ~5k transitions
PlayersGlobalPlayerInstancehumans + AIs same type
Lineagein-memory map + binmother/father/eve, prestige, death
AIAiBase monolith (~7k LOC)professions, craft, combat, LLM hooks

Bottlenecks that force a redesign

  • Full-map arrays — RAM and full/partial scans do not scale to “vast” maps.
  • Coarse mutexes — global / world / player locks; net, AI, web can stall sim.
  • One AI thread — sequential NPC thinking; AI count auto-throttled when slow.
  • Thread-per-connection — poor for large player counts.
  • God-objects — GlobalPlayerInstance + AiBase hard to parallelize or test.
  • Web holds player mutex while building HTML.
  • No structured metrics — hard for automated evolution.

Product identity to preserve (from TODO.MD)

Seasons/winter, temperature, prestige-as-health, classes, coins & hire AI, grave curses, fathers, generational YUM, server AI jobs/commands, reconnect with AI takeover, vanilla client on port 8005, web on 8080.

Fixed timestep (keep 20 Hz game feel)

  1. Drain intent queue (capped per tick)
  2. Movement integration
  3. Vitals (food, heal, heat, exhaust)
  4. Animals / time transitions on hot chunks
  5. Season / biome work (budgeted)
  6. Emit protocol deltas → connection TX queues
  7. Publish metrics / snapshot revision
v1 recommendation: single simulation writer thread + parallel AI + chunked storage. Multi-shard simulation comes after the intent architecture is proven.

6. Large dynamic worlds (no DB)

Vast worlds do not require every tile at 20 Hz. Use residency + catch-up.

Chunk model

  • Chunks e.g. 64×64: biome, floor, sparse objects, helpers, hidden layer, heat, dirty flags, last_sim_tick
  • Hot — players/AI/recent edits → full sim
  • Warm — nearby → reduced rate
  • Cold — time-skip or lazy catch-up on wake
  • On disk — mmap / load when approached

Persistence layers (files only)

LayerMechanism
ContentOneLifeData7 text (read-only)
Worldchunk packs + index
Crash safetyappend-only WAL
Fast bootperiodic snapshots
Lineageappend records + rebuildable indexes
Accountssmall mmap / compacted file
Metricsrotated logs / rings

This continues the spirit of existing SaveFiles/*.bin rotation — just scaled and structured.

7. Server AI NPCs / players

Body (sim)

Same validators as humans: USE, food, combat, death. No special cheating paths.

Mind (workers)

Capture observation → plan → enqueue intents. Never holds world write lock while thinking.

Port strategy for AiBase

  1. Split modules: Survive, Feed, Flee, Hunt, Craft, Profession, Follow, Combat, Temperature
  2. Data-driven priorities / cooldowns later (TOML)
  3. Reverse craft graph from transitions
  4. Hierarchical pathfinding for large maps
  5. Stagger AI ticks so hundreds/thousands do not think simultaneously

LLM path (optional): token bucket rate limit, async HTTP, conversation logs, metrics for latency and remaining calls — never block the sim.

GET /api/metricsJSON / Prometheus

Character page fields

  • Name, age, birth/death, death reason, generation, class
  • Mother / father links, Eve / dynasty
  • Children (reverse index)
  • Prestige, coins, last words
  • HTML/SVG ancestor + descendant tree

Indexes without a DB: append-only records.wal + by_id / by_eve / children index files (rebuildable on boot). HTTP uses mmap; sim only appends on birth/death.

11. Grok Build usage budget plan

Stay under 80% of Super Grok / subscription allowance until refresh, paced evenly so day 1 cannot burn the period.

Canonical docs in this repo: AGENTS.md, docs/GROK_BUILD.md, docs/USAGE_BUDGET.md.

/usage
Run /usage at session start and before expensive work. This shows credit / subscription usage (not the same as /context window fill).
paced usable ≤80% buffer never

Cap = 0.80 × Budget
soft_ceiling(day t) = Cap × (t / D)

Example D=10: day1 ≤8% cumulative, day2 ≤16%, … day10 ≤80%
